# Source-Driven — 源码驱动开发

每个框架特有的代码决策都必须有**官方文档**背书。不要凭记忆实现——
验证、引用、让用户看到你的来源。训练数据会过时、API 会弃用、最佳实践
会演进。本技能确保用户拿到可信的代码：每个模式都能追溯到可查证的权威来源。

## 何时用

- 用户要符合框架当前最佳实践的代码
- 写样板/脚手架/会被全项目复制的模式
- 用户明确要"文档化、已验证、正确"的实现
- 实现框架有推荐做法的功能（表单、路由、数据获取、状态管理、鉴权）
- 审查/改进用框架模式的代码
- 任何"凭记忆写框架代码"的时刻

**不用**：
- 正确性与版本无关（重命名、改错别字、移动文件）
- 所有版本行为一致的纯逻辑（循环、条件、数据结构）
- 用户明确要速度优先（"快点做"）

## 流程

### 1. 识别框架决策点

写代码前标记哪些地方依赖框架特定 API/模式（不是纯逻辑）。

### 2. 查官方文档（验证）

- 优先官方文档（框架官网/官方仓库 README）。
- 确认当前版本：查 changelog/迁移指南，确认没在用弃用 API。
- 记录来源：URL + 版本 + 相关片段。

### 3. 引用来源（可见性）

- 实现时在注释/交付说明里标注来源：
  `// 来源: docs.react.dev/... (React 19)`
- 让用户能自己点开核对。

### 4. 交付时给来源清单

```
## 实现说明
- 数据获取：官方推荐 SWR 模式（来源: …）
- 路由：App Router（来源: …）
- 状态：…（来源: …）
- 注意：X API 已弃用，用 Y 替代（来源: …）
```

## 纪律

- 不凭记忆断言 API 行为；不确定就查。
- 训练数据过时 ≠ 代码正确；框架大版本升级时重新验证。
- 与 api-design 配合：新接口设计也应有文档依据。
- 与 code-review 配合：审查时同样要求来源（"这个 API 在哪文档？"）。

## 边界

- 纯逻辑/不依赖版本的部分不需要来源（避免过度仪式）。
- 用户明确要快时，说明"快速实现未逐条验证来源"，让用户知情。
