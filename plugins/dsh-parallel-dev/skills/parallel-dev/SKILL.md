# Parallel Dev — 并行功能开发

把大功能拆成并行工作流，通过文件所有权与接口契约避免冲突，最后干净集成。

## 何时用

- 把功能拆给并行实现
- 在 agent 之间划分文件所有权
- 设计并行流的接口契约
- 选择集成策略（垂直切片 vs 水平分层）
- 管理并行开发的分支/合并

## 1. 文件所有权

- **一人一域**：每个文件/目录只有一个 owner，避免同时改。
- 共享文件（配置/入口）尽量少，或归主导者统一改。
- 所有权清单写下来（谁改哪些路径），防止越界。

## 2. 接口契约先行

并行实现前，先定义接口契约：

- 模块间 API：函数签名、数据类型、错误约定。
- 数据格式：请求/响应 schema、字段含义。
- 依赖边界：谁提供什么、谁消费什么。

**好处**：实现者可以对着契约开发，不需要等对方的实现 ready。

## 3. 避免冲突

- 按文件所有权开发，合并冲突最小化。
- 契约变更走主导者统一改（不各自为政）。
- 共享依赖版本锁定（不并行升级）。
- 分支短命、频繁集成（参考 git-workflow 主干开发）。

## 4. 集成策略：垂直切片 vs 水平分层

| 策略 | 描述 | 适用 |
|---|---|---|
| 垂直切片 | 每个 worker 完成一个完整功能（前端+后端+数据） | 功能边界清晰、独立交付 |
| 水平分层 | 按层分工（全前端/全后端/全数据） | 层间契约稳定、团队技能分层 |

- **垂直切片优先**：端到端价值早可见、依赖少、集成早。
- 选水平分层时，接口契约必须非常稳定（跨层依赖多）。

## 5. 并行工作流

1. 拆工作流（按功能切片或层）。
2. 定文件所有权 + 接口契约（先写下来）。
3. 并行实现（每流独立验证）。
4. 频繁集成（每流完成即合，尽早暴露冲突）。
5. 整体验收（端到端测试）。

## 输出

- 工作流划分 + 文件所有权清单
- 接口契约文档
- 集成顺序与验证计划

## 边界

- 并行不总是更快：任务间强耦合时串行更好（参考 agent-teams 判断）。
- 契约设计要投入时间，但它省下的集成成本通常更大。
