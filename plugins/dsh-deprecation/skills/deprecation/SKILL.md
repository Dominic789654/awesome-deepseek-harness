# Deprecation — 弃用与迁移

**代码是负债，不是资产。** 每行代码都有持续维护成本——修 bug、更新依赖、
打安全补丁、新人上手。弃用 = 移除不再"赚回成本"的代码的纪律；
迁移 = 把用户安全地从旧系统搬到新系统。

大多数工程组织擅长"建造"，很少擅长"拆除"。本技能弥补这个缺口。

## 何时用

- 用新系统/API/库替换旧系统
- 下线不再需要的功能
- 合并重复实现
- 移除"没人拥有但人人依赖"的死代码
- 规划新系统的生命周期（弃用规划从设计时就该开始）
- 决定维护遗留系统还是投资迁移

## 核心原则

### 代码是负债

- 每个功能都要回答：它还在产生价值吗？维护成本值吗？
- 不因"历史原因"保留；也不因"用的人多"无限期维护——用量是迁移计划的输入，
  不是不迁移的理由。

### 弃用规划从设计时开始

新系统上线第一天就规划：怎么弃用旧系统、迁移窗口多长、谁负责。

## 弃用流程

### 1. 盘点与决策

- 列出要弃用/保留的资产与调用方（grep 全部使用点）。
- 决策：维护 vs 迁移 vs 下线（按价值/成本/风险）。
- 记录决策与理由（ADR）。

### 2. 制定迁移计划

```markdown
## 迁移计划：<旧系统> → <新系统>

- **范围**：<API/功能/数据清单>
- **调用方清单**：<谁在用，怎么用>
- **兼容策略**：<并行运行？双写？兼容层？>
- **阶段**：
  1. 新系统就绪 + 双写（验证一致性）
  2. 读流量切换（灰度）
  3. 写流量切换
  4. 旧系统只读 → 下线
- **回滚方案**：<每阶段的回滚条件与操作>
- **时间表与负责人**：…
```

### 3. 安全迁移

- **并行运行**：新旧并存，验证新系统正确性（数据对比/一致性检查）。
- **灰度切换**：按流量/用户逐步切换，随时可回滚。
- **数据迁移**：备份、校验、幂等重放；迁移工具可重复执行。
- **兼容层**：必要时提供 shim/适配层减少破坏。

### 4. 弃用执行

- 阶段化弃用：标记 deprecated → 日志警告 → 移除。
- 每阶段有明确时间表与公告（调用方有时间迁移）。
- 移除前确认无活跃调用（监控/日志验证）。

### 5. 清理收尾

- 删除死代码、旧依赖、废弃文档。
- 更新相关文档/README/changelog。
- 庆祝：移除代码是进步（review 时肯定，不当作"删了别人工作"）。

## 纪律

- 弃用是**计划好的移除**，不是悄悄删除；有公告、有时间表、有回滚。
- 每个弃用步骤可回滚、可验证（调用方清零才算完成）。
- 新功能设计时就考虑未来的弃用路径（接口设计参考 api-design 技能）。

## 边界

- 重大数据迁移涉及业务风险，需用户/团队批准执行。
- 涉及外部客户 API 时，遵循对外弃用规范（版本、迁移期）。
