# API Design — API 与接口设计

设计稳定、文档完善、**难被误用**的接口。好的接口让正确的事容易、错误的事
困难。适用于 REST API、GraphQL schema、模块边界、组件 props——任何一段代码
与另一段代码对话的表面。

## 何时用

- 设计新 API 端点
- 定义模块边界/跨团队契约
- 创建组件 props 接口
- 建立影响 API 形态的数据库 schema
- 修改既有公开接口

## 核心原则

### Hyrum's Law（海勒姆定律）

> 只要有足够多的用户，你系统的**所有可观察行为**都会被某些人依赖，
> 无论你在契约里承诺了什么。

含义：
- **每个公开行为都是潜在承诺**——包括未记录的怪癖、错误信息文本、时序、
  顺序。设计时对暴露什么要**刻意**。
- **不泄漏实现细节**——用户能观察到的，就会依赖。
- **设计时就规划弃用路径**——安全移除用户依赖的东西。

### 难误用原则

- 正确用法是默认路径，错误用法要显眼地失败。
- 参数顺序/命名要符合直觉（布尔参数用命名对象，避免 `true/false` 位置错）。
- 返回值类型明确，不返回模糊的 `undefined/null` 混合。
- 错误要可操作：告诉调用者"哪里错、怎么修"。

## REST API 设计

- **资源化**：用名词复数资源（`/users`、`/orders/{id}`），HTTP 方法表达动作。
- **一致性**：统一分页/过滤/排序/错误格式（如 `{error: {code, message}}`）。
- **版本化**：URL 版本（`/v1/`）或 header 版本；破坏性变更必须新版本。
- **状态码语义正确**：200/201/204/400/401/403/404/409/422/429/500。
- **幂等**：PUT/DELETE 幂等；POST 对重试要防御（幂等键）。

## GraphQL 设计

- schema 即契约：类型命名清晰、字段名稳定、避免模糊的通用字段。
- 查询/变更分离；变更返回被改实体（便于客户端更新缓存）。
- 别暴露内部字段名（graph 命名 ≠ 数据库列名）。
- 深度/复杂度限制防滥用。

## 模块边界（内部接口）

- 模块对外只暴露最少必要 API；内部实现细节私有。
- 依赖方向：高层依赖低层，不反向。
- 契约用类型/接口显式声明，不靠"约定俗成"。
- 边界两侧的团队/模块各自可独立测试。

## 变更公开接口时

- 先查调用方（grep/依赖图），评估破坏范围。
- 向后兼容优先（加可选参数、新端点而非改旧）。
- 必须破坏时：新版本 + 弃用期 + 迁移指南 + 移除时间表。

## 输出

- 接口设计文档：资源/端点/字段/状态码/示例 + 设计决策理由（为什么这样）。
- 变更评估：影响范围 + 迁移方案。
