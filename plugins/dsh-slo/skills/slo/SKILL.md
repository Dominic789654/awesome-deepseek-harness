# SLO — SLI/SLO/错误预算

用可衡量的可靠性目标（SLI/SLO）+ 错误预算，在可靠性与创新速度之间取得平衡。

## 何时用

- 定义服务可靠性目标
- 衡量用户感知的可靠性
- 实现错误预算
- 建立基于 SLO 的告警
- 追踪可靠性目标

## SLI/SLO/SLA 层级

- **SLA**（服务等级协议）：对外承诺（合同义务，通常比内部目标宽松）。
- **SLO**（服务等级目标）：内部承诺（比 SLA 严格，给错误预算留空间）。
- **SLI**（服务等级指标）：实际度量（可用性、延迟、错误率、吞吐）。

## 设计流程

### 1. 选 SLI（度量什么）

从用户感知出发，每个关键路径选 1-2 个 SLI：

| 维度 | 示例 SLI |
|---|---|
| 可用性 | 成功请求占比 |
| 延迟 | 满足延迟预算的请求占比（如 p95 < 500ms） |
| 错误率 | 5xx 占比 |
| 吞吐 | 处理速率 |
| 持久性 | 数据成功持久化占比 |

**SLI 公式**：`good / total`（好事占比），如 `2xx+3xx 响应数 / 总响应数`。

### 2. 定 SLO（承诺多少）

- 目标要基于**实际基线**（先测 2-4 周真实数据再定），不要拍脑袋。
- 常见起点：可用性 99.9%（全年 8.8h 停机预算），延迟 p95 < 500ms 满足率 99%。
- **SLO 应比 SLA 严格**：对外承诺 99.9%，对内目标 99.95%，留缓冲。

### 3. 算错误预算（还剩多少"出错额度"）

```
错误预算 = 1 - SLO
月度预算（例 99.9%）= 30 天 × 24h × 60min × (1 - 0.999) ≈ 43 分钟
已消耗 = 实际错误时间 / 预算
```

### 4. 建告警与行动

- **预算消耗告警**：消耗率异常（如 24h 内消耗 > 50% 月预算）→ 告警。
- **预算耗尽策略**：
  - 消耗 < 70%：正常开发。
  - 70-100%：冻结高风险变更，优先修可靠性。
  - 已耗尽：必须回滚/止血，暂停新功能。
- 告警基于**错误预算消耗**而非单个指标尖峰（避免告警疲劳）。

### 5. 定期评审

- 每季度评审 SLO：目标是否仍有意义？SLI 是否真正反映用户感知？
- 随业务变化调整，不僵化。

## 边界

- SLO 是工程权衡，不是 KPI 考核工具——目标是改进系统，不是惩罚团队。
- 具体监控平台（Prometheus/Grafana/Datadog）的配置按实际环境。
