# Microservices — 微服务架构模式

设计微服务架构：服务边界、通信、数据管理、韧性与事件驱动。

## 何时用

- 单体拆微服务
- 设计服务边界与契约
- 实现服务间通信
- 管理分布式数据与事务
- 构建韧性分布式系统
- 服务发现与负载均衡
- 事件驱动架构

## 1. 服务边界

- **按业务能力/子域切**（DDD 子域），不按技术层切（不搞"用户服务按
  controller/service/repo 拆三个服务"）。
- 边界 = 数据所有权：一个服务拥有自己的数据，不共享数据库表。
- 契约显式：API/事件 schema 版本化（参考 api-design）。
- **先问**：这个服务独立部署/独立扩展/独立团队的价值，是否大于拆分成本？

## 2. 服务间通信

- **同步**（REST/gRPC）：请求-响应；注意调用链的级联延迟与失败。
- **异步**（消息/事件）：解耦、削峰；注意最终一致。
- 选择原则：强一致需求 → 同步；解耦/韧性 → 异步。
- 服务发现 + 负载均衡：注册中心/DNS/网格。

## 3. 数据管理（分布式事务）

- **避免跨服务事务**：每个服务拥有自己的数据。
- **Saga 模式**：跨服务流程用 Saga 编排/编排式补偿（成功顺序执行，
  失败按逆序补偿）。
- **事件溯源/最终一致**：事件驱动更新各服务数据，接受短暂不一致。
- CQRS（读写分离）用于复杂查询场景（读模型独立优化）。

## 4. 韧性模式

- **熔断（Circuit Breaker）**：下游故障时快速失败，不拖垮本服务。
- **超时 + 重试**（带退避）：防级联超时；重试要有上限。
- **舱壁（Bulkhead）**：隔离资源池，一个下游故障不影响其它。
- **限流/降级**：过载保护（参考 observability/slo）。
- **幂等**：重试安全（请求幂等键）。

## 5. 事件驱动架构

- 事件是"已发生的事实"（过去时），不是命令。
- 事件 schema 版本化；消费者向前兼容。
- 事件总线/消息队列选型（Kafka/RabbitMQ/云原生）按规模与语义。
- 死信与重放：处理失败事件，可重放恢复。

## 设计自查

- [ ] 服务边界按业务能力，数据不共享
- [ ] 契约版本化
- [ ] 跨服务流程有 Saga/补偿
- [ ] 依赖调用有超时/熔断/重试
- [ ] 事件 schema 版本化 + 死信处理
- [ ] 服务发现与负载均衡已选型

## 边界

- 微服务是手段不是目的：小团队/小系统单体+模块化往往更优。
- 具体技术栈（gRPC/Kafka/网格）按团队熟悉度选型。
