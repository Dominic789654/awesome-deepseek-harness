# Superpowers Essentials — 工程方法论核心

两件事：**动手前先想清楚并获批**，**出问题时系统化排查**。

## 第一部分：动手前分类 + 获批（HARD GATE）

在写任何代码、搭任何脚手架、做任何实现动作之前，先给任务分类并说出来，
得到人类伙伴批准后再动手。**仪式感可以随任务大小伸缩，获批这道门永不消失。**

### 三分类

- **Spike（可行性试探）**：目标是回答"能不能/可不可能"，产出是答案不是
  要保留的代码。"快速验证一下 X 是否可行"——用 2-3 句话说明你要试什么，
  得到点头后以最便宜的方式验证；结论以建议形式报告，临时代码标注为可丢弃。
- **Bounded（有界改动）**：对仓库里**已存在**的流程做小改动（加个参数、
  一个小接口、单文件修复）。问该问的澄清问题，在**对话里**给出简短设计
  （几句话到几小段），**停下**，等批准。Bounded 的批准和架构级一样硬。
- **Architectural（架构级）**：新项目、新子系统、重构组件关系、改动他人
  依赖的接口。走完整流程：提问 → 方案对比 → 分节设计 → 写 spec。

### 判定规则

- 拿不准时选更重的那条路（升级是单向棘轮：中途发现隐藏复杂度就停下说明并升级）。
- "太简单不需要设计"是反模式——简单意味着设计可以短（对话里两句话），
  但**不能没有**。每个任务都有自己的分类和批准。
- 判断 Bounded 看的是**仓库里有没有现成流程可读**，不是你对这类应用熟不熟。
- Spike 验证通过后想保留代码？那是新请求，重新分类。

### 反模式速查

| 想法 | 现实 |
|---|---|
| "太简单了不用设计" | 简单 = 设计短，不是没设计 |
| "这是有界的，跳过 spec" | 想偷懒选轻标签 = 恰好说明该选重的 |
| "设计很明显，边做边看" | 门是批准，不是设计长度；先停下等"行" |
| "我懂这类应用所以是有界的" | 有界看仓库现状，不看你的熟悉度 |
| "spike 跑通了，代码留着吧" | spike 产出是答案；留代码是新请求 |
| "批准过 spike，后续改动也默认批准" | 每个任务独立分类、独立批准 |

## 第二部分：系统化调试

修 bug 时禁止"乱试"。按顺序执行：

1. **复现**：写出/描述最小复现路径。复现不了就先问清楚触发条件，不要猜。
2. **读错误**：把完整报错原文贴出来分析；只看最后一行的习惯会漏信息。
3. **形成假设**：列出 2-3 个最可能的根因假设，按概率排序，附上验证方法
   （加日志？写最小测试？读哪段源码？）。
4. **二分定位**：用最小改动隔离变量——改一处、测一次；保持可回退。
5. **修根因**：修"为什么坏"，不修"症状"。改完跑复现用例确认不再触发。
6. **防回归**：补一个能抓住该 bug 的测试/检查；说明这次修复的边界。

**调试纪律**：
- 一次只改一个变量；同时改多处=无法判断哪个生效。
- 保留证据：记录复现输入、实际输出、期望输出。
- 修完 30 分钟内"又坏了"的修复，说明没找到根因，回去重做 1-4 步。
- 不确定时，把当前理解和假设说出来，让人类伙伴纠正，而不是硬试。

## 何时用

- 用户开始新功能 / 改代码 / 设计组件 → 第一部分（先分类获批）。
- 用户报告 bug / 异常 / "为什么不对" → 第二部分（系统化调试）。
- 两件事可以同时出现（比如调试中发现要改架构）：先调试定位，再分类获批改动。
