# Doc Co-Authoring — 文档协作撰写

结构化协同创作工作流：主动引导用户走过三阶段——
上下文收集 → 细化与结构 → 读者测试。目标是文档在别人读时
（包括贴进 AI 时）真正有效。

## 何时提供

**触发**：用户提到写文档（"写个文档"/"起草提案"/"创规格"）或
特定类型（PRD/设计文档/决策文档/RFC）或开始实质性写作任务。

**初始提议**：提供三阶段工作流并解释；用户拒绝就自由发挥，
接受就进入阶段一。

## 1. 阶段一：上下文收集

目标：弥合用户所知与 AI 所知的差距。

**元上下文问题**：
1. 这是什么类型的文档？（技术规格/决策文档/提案…）
2. 主要受众是谁？
3. 读者读后期望的影响是什么？
4. 有模板或特定格式吗？
5. 其他约束或上下文？

允许用户速记或倾倒信息。有模板/现有文档 → 读取（链接用集成获取，
文件直接读）。编辑现有共享文档 → 检查无 alt-text 的图片：
告诉用户"别人用 AI 读文档时看不到它们"，问是否生成 alt-text。

## 2. 阶段二：细化与结构

- 逐节迭代：头脑风暴 + 编辑，每节定稿再进下一节
- 保持结构服务于读者与影响目标
- 每节追问：这节解决读者什么问题？

## 3. 阶段三：读者测试

- 用**无上下文的新会话**测试文档：让它读文档并执行/回答
- 找出盲区：假设未说明、步骤缺失、术语未定义
- 修复后重测（文档要能"冷启动"工作）

## 4. 自查清单

- [ ] 元上下文五问覆盖（类型/受众/影响/模板/约束）
- [ ] 模板/现有文档已读取，图片有 alt-text
- [ ] 逐节细化、结构服务读者
- [ ] 新会话读者测试通过（无盲区）
- [ ] 修复后重测
- [ ] 用户选择自由模式时尊重其选择

## 边界

- 文档是"给别人读 + 给 AI 读"的产品：冷启动测试是核心价值。
- 与内部沟通（类型模板）互补：本技能是协作流程，模板是内容格式。
