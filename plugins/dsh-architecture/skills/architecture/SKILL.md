# Architecture — 架构模式

用经过验证的后端架构模式（Clean / Hexagonal / DDD）构建可维护、可测试、
可扩展的系统。

**输入**：一个服务边界或模块。
**产出**：分层结构 + 清晰依赖规则 + 接口定义 + 测试边界。

## 何时用

- 从零设计后端服务/微服务
- 重构业务逻辑与 ORM/HTTP 纠缠的单体
- 拆分系统前建立限界上下文
- 调试基础设施代码渗入领域层的依赖循环
- 创建不需要真实数据库就能跑用例测试的代码库
- 实现 DDD 战术模式（聚合、值对象、领域事件）

## 1. 分层与依赖规则

- **内层不依赖外层**：领域层（核心）不 import 基础设施（框架/DB/HTTP）。
- 依赖方向向内：外层依赖内层，内层定义接口，外层实现。
- 典型分层：Controller/API → Application（用例）→ Domain（核心）→
  Infrastructure（实现）。

```
┌──────────────┐
│ Infrastructure│ (DB/HTTP/框架实现)
├──────────────┤
│ Application  │ (用例编排)
├──────────────┤
│ Domain       │ (业务规则核心) ← 依赖只指向这里
└──────────────┘
```

## 2. 三种模式速览

| 模式 | 核心思想 | 适用 |
|---|---|---|
| Clean | 依赖规则 + 用例为中心 | 通用后端 |
| Hexagonal | 端口-适配器（业务核心 ↔ 外部世界通过端口） | 多适配器场景 |
| DDD | 限界上下文 + 战术模式 | 复杂领域 |

## 3. DDD 战术模式

- **聚合（Aggregate）**：一组一致性边界内的实体，通过聚合根访问。
- **值对象（Value Object）**：不可变、按值相等（金额、地址）。
- **实体（Entity）**：有身份、可变的领域对象。
- **领域事件（Domain Event）**：领域内发生的事实，驱动后续逻辑。
- **仓库（Repository）**：领域层的集合抽象，实现由基础设施提供。
- **应用服务（Use Case）**：编排用例，不承载业务规则。

## 4. 测试边界

- 领域/用例测试**不需要真实 DB/HTTP**（依赖注入接口，mock 实现）。
- 快速测试：核心逻辑可单测；慢的集成测试在外层。
- 依赖注入是手段：让内层不感知具体实现。

## 架构自查

- [ ] 依赖方向向内（无反向 import）
- [ ] 领域层无框架/DB 依赖
- [ ] 用例可脱离基础设施测试
- [ ] 聚合边界清晰（一致性边界）
- [ ] 无依赖循环
- [ ] 分层职责清晰（不越层调用）

## 边界

- 架构模式服务于可维护性，不为模式而模式（小系统可简化）。
- 与 domain-modeling（术语/模型）和 microservices（服务间）互补。
