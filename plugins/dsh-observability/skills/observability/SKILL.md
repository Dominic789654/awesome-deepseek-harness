# Observability — 可观测性与埋点

让系统**可被理解**：出了问题能回答"发生了什么、为什么、影响多大"。
三大支柱：日志（Logs）、指标（Metrics）、追踪（Traces）。

## 何时用

- 添加/改进日志
- 为服务建立指标
- 实现分布式追踪
- 设计告警
- 排查"黑盒"系统

## 三支柱

| 支柱 | 回答什么 | 特点 |
|---|---|---|
| 日志 | 发生了什么（事件细节） | 高信息量、高成本、按需查 |
| 指标 | 系统健康（聚合数值） | 低成本、趋势、告警 |
| 追踪 | 请求生命周期（跨服务） | 定位慢路径/依赖问题 |

三者配合：指标发现异常 → 追踪定位请求路径 → 日志看细节。

## 1. 结构化日志

- **JSON 格式**（machine-readable），字段统一：时间戳、级别、服务、
  请求 ID、消息、结构化上下文。
- **级别正确**：debug（调试）/ info（常规）/ warn（可恢复问题）/
  error（需关注）/ fatal（崩溃）。
- **包含请求上下文**：request_id / trace_id / user_id / 耗时。
- **不记录敏感信息**：密钥、PII、完整请求体（参考 security-hardening）。
- **有意义的日志消息**：说清"发生了什么 + 关键数据"，不只是状态码。

## 2. 指标

- 经典四类（RED / USE）：
  - **Rate**（请求速率）、**Errors**（错误率）、**Duration**（延迟分位）。
  - **Utilization**（利用率）、**Saturation**（饱和）、**Errors**。
- 打点要点：统一命名、带标签（service/endpoint/status）、
  直方图用于延迟（记录分位）。
- 从用户感知出发：可用性、延迟、错误率（参考 slo 技能选 SLI）。

## 3. 分布式追踪

- 请求进入时生成 trace_id，跨服务传递（header 注入）。
- 每个 span 记录：操作名、开始/结束、状态、关键属性。
- 采样策略：高流量只采样部分（如 10%），错误全采。
- 用途：定位慢依赖、瀑布图看时间分布、跨服务错误定位。

## 4. 告警设计

- **基于 SLO 的告警**（参考 slo 技能）：按错误预算消耗告警，而非单个尖峰。
- 告警四要素：条件、严重度、负责人、行动手册（runbook 链接）。
- **减少噪音**：告警要有行动价值；没行动的告警删掉。
- 分级：page（立即打扰）/ ticket（工作时间处理）/ 日志（仅记录）。

## 实现清单（加埋点时自查）

- [ ] 关键路径有日志（含 request_id 上下文）
- [ ] 服务有 RED/USE 指标
- [ ] 跨服务调用带 trace_id
- [ ] 错误路径有 error 级日志（含堆栈/上下文）
- [ ] 告警有 runbook 链接
- [ ] 无敏感信息进日志

## 边界

- 具体平台（Prometheus/Grafana/OpenTelemetry/Datadog）配置按实际环境。
- 埋点适度：只加会"行动"的观测，不加装饰性日志。
