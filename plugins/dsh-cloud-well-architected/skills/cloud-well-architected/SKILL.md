# Cloud Well-Architected — 六支柱架构评审

基于 Google Cloud Well-Architected Framework 的设计原则与建议，
评估、设计或改进云工作负载。

## 何时用

- 评估/设计/改进云架构（可靠性/成本/安全/性能…）
- 上云前架构评审、灾备设计、SLO 设定
- 故障复盘与恢复测试

## 1. 六支柱总览

| 支柱 | 关注 |
|------|------|
| **可靠性** | 可用性、韧性、故障恢复、灾备 |
| **成本优化** | 资源利用率、成本效益 |
| **运维卓越** | 运营流程、监控告警、自动化 |
| **性能优化** | 性能效率、资源匹配 |
| **安全** | 身份/数据/网络/应用安全 |
| **可持续性** | 环境足迹、资源效率 |

## 2. 可靠性支柱核心原则（示例）

- **按用户经验目标定义可靠性**：测用户实际体验，非仅基础设施指标
- **设现实 SLO**：监控信号 + 错误预算 + 用户体验目标平衡成本
- **资源冗余**：跨区域/可用区复制关键组件，消除单点故障
- **水平扩展**：加实例应对负载波动 + 主动容量规划
- **可观测性**：golden signals（延迟/流量/错误/饱和度）+ 告警阈值
- **优雅降级**：依赖失败时保持核心功能（熔断器、指数退避+抖动重试、
  自定义错误页/静态回退）
- **恢复测试**：持续模拟故障验证恢复流程；定期测备份/恢复满足 RTO/RPO
- **无指责复盘**：全面调查根因 + 防复发措施

## 3. 评估工作流

1. 明确评估范围与目标支柱
2. 对照设计原则逐项检查（用户经验目标/SLO/冗余/可扩展性…）
3. 识别差距与风险（单点故障/无恢复测试/无错误预算…）
4. 产出改进建议（按优先级 + 对应产品/功能）
5. 落地并持续验证（模拟故障/恢复演练）

## 4. 自查清单

- [ ] 目标支柱明确（可靠性/成本/安全…）
- [ ] 可靠性按用户体验目标定义
- [ ] SLO + 错误预算就位
- [ ] 冗余消除单点故障
- [ ] golden signals 监控 + 告警
- [ ] 恢复测试满足 RTO/RPO
- [ ] 无指责复盘文化

## 边界

- 框架给原则与建议，具体数值（SLO 目标/RTO）由业务定。
- 各云厂商均有对应框架（Google/AWS/Azure）——原则互通。
