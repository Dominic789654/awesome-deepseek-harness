# Before You Build — 建前风险预审

动工前跑一次紧凑的 pre-mortem：目的不是阻止建设，而是找出最高风险假设、
最小验证步骤、以及应推迟到证据改善再做的范围。

## 何时用

用户要建/发布以下内容时：
- 新产品、MVP、原型、落地页、SaaS、市场、内容站、agent 工作流、内部工具
- 采纳/收入/留存/信任/分发影响不明的大功能
- 公开上线资产（弱定位会浪费开发与推广）

**跳过**：纯实现修复、重构、测试修补、依赖更新、已有明确验收标准的变更。

## 1. 七维风险检查

- **需求**：是否有证据表明特定买家/用户急需？
- **定位**：目标用户能否一句话说清它是什么、为何重要？
- **变现**：是否有可信的付费/预算/战略价值路径？
- **留存**：用户首次试用后有理由回来吗？
- **信任**：产品是否需要用户难以接受的信用、数据访问、集成或行为改变？
- **分发**：有可重复触达目标用户的方式吗？
- **功能采纳**：会改变用户行为，还是只是加表面积？

## 2. 输出格式（简短、面向决策）

1. **风险结论**：低/中/高 + 一句话理由
2. **最关键假设**：最可能搞垮项目的那个假设
3. **先找的证据**：继续建之前的最小有用信号
4. **下一步**：一个具体验证步骤或缩减的构建范围
5. **推迟**：现在先不建什么

## 3. 原则

- 对薄弱证据直接说，但不否定用户的想法
- 偏好更小的验证步骤，而不是大研究计划
- 区分产品风险与工程难度
- 已验证的想法：说明什么证据使其低风险，建议最小实现切片
- 缺事实就点名缺什么证据，不编造市场论断

## 4. 自查清单

- [ ] 七维风险过了一遍（需求/定位/变现/留存/信任/分发/采纳）
- [ ] 风险结论 + 一句话理由
- [ ] 单个最关键假设已点名
- [ ] 最小验证步骤具体可执行
- [ ] 应推迟范围明确
- [ ] 未编造缺失的市场证据

## 边界

- 这是预审不是市场研究：快速判断 + 小验证，别陷入大报告。
- 与产品/业务分析互补：预审在前（要不要建），分析在后（怎么建/多大）。
