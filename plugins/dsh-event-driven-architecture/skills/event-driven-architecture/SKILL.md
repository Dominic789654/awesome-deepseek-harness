# Event-Driven Architecture — 事件驱动架构

用事件把读写模型、状态溯源与分布式事务串起来：CQRS + 事件溯源 + 投影 + Saga。

## 何时用

- 分离读写关注点、独立扩缩读/写
- 构建事件溯源系统
- 跨微服务的分布式事务（2PC 不可用时）
- 长时运行业务工作流（订单、审批、预订）
- 复杂查询场景与高性能报表

## 1. CQRS（命令查询职责分离）

- **Command**：改变状态的意图 → Command Handler 校验并执行 → 写模型。
- **Query**：数据请求 → Query Handler 从读模型取数。
- **Event**：状态变更的记录，从写模型流向投影（Projector）更新读模型。
- 读写模型**独立演化**：读模型按查询去规范化（denormalize）。

**要**：命令与查询模型分离；接受最终一致（定义可接受延迟 SLA）；
命令里做校验；事件版本化（schema 演进）。
**不要**：不在 command 里查询；不耦合读写 schema；
不过度设计（先简单，必要时再上）。

## 2. 事件溯源与事件存储

- 事件是**不可变事实**：只追加（append-only）、按流/全局有序、版本化（乐观并发）。
- 流 ID 含聚合类型（`Order-{uuid}`）；事件带 correlation/causation ID（链路追踪）。
- 从第一天就版本化事件；用事件 ID 做幂等去重。

技术选型：EventStoreDB（纯事件溯源）/ PostgreSQL（已有 PG 栈，需手写）/
Kafka（高吞吐流，不擅长按流查询）/ DynamoDB（serverless）/ Marten（.NET）。

**不要**：不更新/删除事件；不存大 payload（事件保持小）；
不跳过乐观并发；不忽略背压（慢消费者）。

## 3. 投影（Projection）

- 订阅事件流 → 维护读模型（聚合视图/报表/搜索索引）。
- 投影必须**可重放**（从头重建读模型）；幂等处理重复事件。
- 与 CQRS 读模型配合，读路径专为查询优化。

## 4. Saga（分布式事务与补偿）

无 2PC 的分布式事务：编排（Orchestrator 指挥）或编排舞（Choreography 事件驱动）。

**输入**：服务边界与归属、哪些步骤必须原子/可最终一致、每步失败模式与重试策略、SLA。
**产出**：有序步骤 + 命令 + 补偿命令；每步超时；监控（状态机指标、卡死检测、DLQ 恢复）。

**要**：每步幂等（命令可能因重连重放）；补偿是**最关键路径**要精心设计；
correlation ID（saga_id）贯穿所有事件与日志；每步独立超时；显式测试补偿路径
（集成测试在每步索引注入失败）。
**不要**：不假设即时完成（Saga 是异步的）；不跳过补偿测试；
不在 saga 步骤里同步调用服务（用异步消息）；不忽略部分失败（部分执行仍需补偿）；
不用全局超时。

**排查**：Saga 卡在 COMPENSATING → 补偿 handler 抛异常未发布完成事件 →
补偿消费者加 DLQ 处理，保证每个补偿动作都发布结果事件。

## 5. 自查清单

- [ ] 读写模型分离、读模型按查询去规范化
- [ ] 事件只追加、版本化、幂等去重
- [ ] 投影可重放、读模型可重建
- [ ] Saga 每步幂等 + 独立超时 + correlation ID 贯穿
- [ ] 补偿路径已显式测试（每步注入失败）
- [ ] 一致性 SLA（可接受延迟）已定义

## 边界

- 事件溯源与 CQRS 复杂度高：查询/报表简单时别硬上，先单体 + 事件。
- Saga 与事件存储选型依赖团队栈；Kafka 类系统注意按流查询限制。
