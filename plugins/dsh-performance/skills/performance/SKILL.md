# Performance — 性能优化

系统的、以测量驱动的性能优化流程。**先测量，再优化**——不测量的优化
是猜测，猜错的优化是浪费。

## 何时用

- 页面/接口响应慢
- 加载时间长
- 内存占用高
- 高延迟/低吞吐
- 用户报告卡顿

## 优化流程

### 1. 测量先行

- 建立基线：量化"慢"（响应时间、吞吐、内存、CPU、TTFB）。
- 用工具：浏览器 DevTools（Network/Performance）、profiler、APM。
- 记录环境：硬件、浏览器、网络、数据量。
- **优化前后对比同一基准**。

### 2. 定位瓶颈

- 遵循"80/20"：先找最大的瓶颈（瀑布图最长的块、profiler 最热的函数）。
- 分层排查：网络 → 后端（DB 查询/CPU/IO）→ 前端（渲染/JS/资源）。
- 复杂度分析：找意外的 O(n²)、N+1 查询、重复计算。

### 3. 常见优化手段（按性价比）

- **后端**：
  - N+1 查询 → join/预加载。
  - 重复计算 → 缓存（结果缓存、查询缓存）。
  - 大响应 → 分页、字段裁剪、压缩。
  - 同步阻塞 → 异步化、批处理。
- **前端**：
  - 资源体积 → 代码分割、tree-shaking、压缩、图片格式（WebP/AVIF）。
  - 渲染阻塞 → 懒加载、骨架屏、虚拟列表。
  - JS 开销 → 减少重渲染、memo、避免布局抖动。
- **数据库**：
  - 缺索引 → 按查询模式加索引。
  - 全表扫描 → 索引覆盖。
  - 缓存策略 → 读多写少加缓存层。

### 4. 验证与回归

- 优化后重测同一基准，记录提升幅度。
- 加性能回归检查（预算：bundle 大小、关键路径时长）。
- 确认优化没引入正确性问题（功能测试仍过）。

## 性能预算

为关键路径设定预算并守护：
- LCP（最大内容绘制）< 2.5s
- TTI（可交互时间）< 3.8s
- bundle 体积预算（如 gzip 后 < 200KB）
- API p95 延迟预算

## 输出

- 基线测量结果（before/after 对比表）
- 瓶颈分析（证据驱动的结论）
- 优化项清单（每项：问题 → 手段 → 预期收益 → 验证方式）
- 性能预算建议

## 边界

- 不为微优化牺牲可读性；先优化"慢得明显"的，再谈细节。
- 优化前先确认"需要优化吗"（Pareto：20% 的优化解决 80% 的问题）。
