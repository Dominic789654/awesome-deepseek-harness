# Merge Conflicts — 解决合并/变基冲突

五步流程，稳定解决 git 合并/变基冲突。

## 流程

### 1. 看清现状

查看合并/变基的当前状态：git 历史、冲突文件列表。确认冲突范围再动手。

### 2. 找到各方意图

对每个冲突，理解**每一方**为什么这么改、原始意图是什么：
- 读 commit message
- 查 PR
- 查原始 issue/ticket
- 必要时读冲突双方周边的代码上下文

不要只看冲突标记本身——冲突的本质是"两边都改动了同一处，且都合理"。

### 3. 逐块解决

对每个 hunk：
- **尽量保留双方意图**（两边改动可能兼容，只是位置重叠）。
- 确实不兼容时，选择符合**本次合并的既定目标**的那一方，并**记录权衡**。
- **不要发明新行为**——解决冲突不是重构机会。
- 永远解决，不要 `--abort`（abort 等于丢弃这次合并的全部工作，
  包括已解决的部分；只有确认合并方向错了才考虑）。

### 4. 跑自动化检查

发现项目用哪些检查（README / package.json scripts / CI 配置），
按顺序跑：类型检查 → 测试 → 格式化。修复合并破坏的任何东西。

### 5. 完成合并/变基

- 合并：staging 全部改动，提交（保留标准合并提交信息，可补充解决说明）。
- 变基：`git rebase --continue`，直到所有提交都重放完成。

## 边界

- 冲突解决要保守：目标是"把两边的工作都保住"，不是"借机重构"。
- 一个 hunk 的解决会连锁影响其它 hunk 时，先解决依赖上游的。
- 遇到无法判断意图的冲突，列出选项让用户决定，不要猜。
