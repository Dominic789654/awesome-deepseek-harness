# TDD — 测试驱动开发

先写一个失败的测试，再写让它通过的代码。修 bug 时，先用测试复现 bug
再修。**测试是证明——"看起来对"不算完成。** 有好测试的代码库是 agent
的超能力；没测试的代码库是负债。

## 何时用

- 实现任何新逻辑/行为
- 修任何 bug（Prove-It 模式）
- 修改现有功能
- 添加边界情况处理
- 任何可能破坏现有行为的改动

**不用**：纯配置变更、文档更新、无行为影响的静态内容。

## 先摸清测试栈

- 项目用什么测试框架？（jest/vitest/pytest/go test…）
- 测试命令是什么？怎么跑单个测试？
- 现有测试风格/约定（命名、组织、mock 方式）？
- 新代码遵循既有约定，不发明新风格。

## TDD 循环（红-绿-重构）

1. **红**：写一个失败的测试（先想清楚行为，再写测试）。
2. **绿**：写最小实现让它通过（不做多余功能）。
3. **重构**：在测试保护下清理代码（保持绿）。

## Prove-It 模式（修 bug）

1. **写复现测试**：先写一个能复现 bug 的测试（红）。
2. **修 bug**：改代码让它通过（绿）。
3. **防回归**：保留该测试——它就是回归防线。

**纪律**：没有复现测试就"修复"的 bug，等于没修（可能根本没修对，
也可能修了但没人知道会复发）。

## 测试质量要点

- **测行为不测实现**：断言输入输出，不锁定内部调用细节。
- **边界情况**：空、null、0、负数、超长、极端值。
- **错误路径**：不只测快乐路径。
- **测试本身要简单**：一个测试一个断言主题；复杂 setup 是坏味道。
- **快速**：测试要快才能常跑；慢测试分到集成层。

## 何时"可以"不 TDD

- 纯配置/文档/静态内容。
- 一次性脚本（跑完即弃）。
- 用户明确要求速度优先且接受无测试。

## 边界

- 测试栈与框架按项目实际；本技能提供方法论不绑定工具。
- 存量代码补测试时，优先给高风险/常变逻辑补（不追求 100% 覆盖）。
