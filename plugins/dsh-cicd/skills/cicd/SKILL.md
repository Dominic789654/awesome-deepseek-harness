# CI/CD — 持续集成与交付

自动化质量门禁，让任何变更不通过测试/lint/类型检查/构建就无法进入生产。
CI/CD 是其他所有技能的**执行机制**——它捕捉人和 agent 漏掉的错误，
且对每个变更都一致地执行。

## 核心理念

### Shift Left（左移）

尽可能早地捕捉问题：lint 阶段抓到的 bug 花几分钟；生产环境抓到的花几小时。
检查向上游移动——静态分析在测试前，测试在预发布前，预发布在生产前。

### Faster is Safer（更快更安全）

小批量 + 高频发布**降低**风险：3 个变更的部署比 30 个变更的容易调试。
频繁发布建立对发布流程本身的信心。

## 何时用

- 搭建新项目的 CI 管线
- 添加/修改自动化检查
- 配置部署管线
- 变更应触发自动化验证时
- 调试 CI 失败

## 质量门禁设计

每个 PR/推送触发（按序）：

1. **静态分析**：lint + 格式检查（最快，最先跑）。
2. **类型检查**：TypeScript/编译期检查。
3. **单元测试**：快速、隔离的测试。
4. **构建**：产物可构建。
5. **集成/端到端测试**：跨模块流程。
6. **安全检查**：依赖审计、密钥扫描。
7. **（可选）预览部署**：PR 环境供人工验证。

**门禁原则**：
- 门禁失败即阻断合并（不"先合后补"）。
- 每级失败信息要可操作（告诉开发者怎么修）。
- 门禁逐步变慢但更全面（先快后全）。

## 部署策略

- **小批量高频**：短发布周期。
- **蓝绿/金丝雀**：新版本灰度，可快速回滚。
- **回滚优先**：部署失败先回滚再调查，不在生产上debug。
- **部署即代码**：管线配置入库（Infrastructure as Code），可评审可回滚。

## 调试 CI 失败

1. 读完整失败日志（不只看最后几行）。
2. 复现：本地跑相同命令（用同一依赖版本）。
3. 区分：是代码问题、测试问题、还是环境问题（flaky）。
4. flaky 测试：标记并修复，不忽略。
5. 修复后重跑验证。

## 输出

- 管线配置（CI 平台 YAML/配置 + 各阶段说明）
- 质量门禁清单（每级检查 + 失败处理）
- 部署策略说明（发布流程 + 回滚方案）

## 边界

- 具体 CI 平台（GitHub Actions/GitLab CI/Jenkins）语法按平台。
- 不擅自部署到生产；部署动作需用户确认。
