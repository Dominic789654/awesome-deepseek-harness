# Docs & ADR — 文档与架构决策记录

记录**决策**，不只是代码。最有价值的文档捕捉**为什么**——导致决策的
上下文、约束与权衡。代码展示"建了什么"；文档解释"为什么这样建"和
"考虑过哪些替代方案"。

## 何时用

- 做出重要架构决策
- 在竞争方案间选择
- 新增/修改公共 API
- 上线改变用户可见行为的功能
- 让新成员（或 agent）上手项目
- 反复解释同一件事时（该写成文档了）

**不用**：显而易见的代码不写文档；不要写重复代码内容的注释；
一次性原型不写文档。

## ADR（架构决策记录）

最高价值的文档。捕捉重大技术决策背后的推理。

### 何时写 ADR

三个条件**同时**成立：
1. **难逆转**：以后改主意成本高
2. **无上下文会惊讶**：未来读者会问"为什么这么做"
3. **真实权衡**：有真正的替代方案，因具体理由选其一

缺任一条件 → 不写（写个短注释即可）。

### ADR 格式

```markdown
# ADR-000N: <标题>

- **状态**：已接受 / 提议 / 已废弃
- **日期**：YYYY-MM-DD

## 背景
- 问题与约束：…
- 触发事件：…

## 决策
- 选择了什么：…
- 决策理由：…

## 被否方案
- 方案 A：为什么没选
- 方案 B：为什么没选

## 后果
- 正面：…
- 负面 / 权衡：…

## 后续
- 相关 ADR / 待观察项：…
```

编号递增（ADR-0001, 0002...），放 `docs/adr/` 目录。

## 文档策略

- **README 写"怎么用"**，ADR 写"为什么这样"。
- **注释写"为什么"**，不重复代码本身（`// 为什么这样做` 而非 `// 这段代码做 X`）。
- **文档要可维护**：文档与代码不符时，要么改文档要么改代码（二选一，
  不留过期文档）。
- **文档写给读者**：未来的人和 agent；用他们需要的信息组织。

## 何时不写文档

- 代码自解释（显而易见的逻辑）。
- 一次性/临时原型。
- 频繁变化会立刻过时的细节（接口签名有源码/类型作证）。
- 没人会读的长篇大论（写短文档，信息密度优先）。

## 输出

- 决策场景 → ADR（按格式）。
- 功能/模块 → README 节 + 关键"为什么"注释。
- 反复解释的问题 → 沉淀为 FAQ/指南。

## 边界

- 与 domain-modeling 互补：那个维护术语表，这个记录决策。
- 文档适度：信息密度 > 篇幅；能少写就少写，但要写就写对。
