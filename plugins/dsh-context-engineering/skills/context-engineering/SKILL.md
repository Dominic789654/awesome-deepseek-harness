# Context Engineering — 上下文工程

在正确的时间给 agent 喂正确的信息。上下文是 agent 输出质量的**最大杠杆**：
太少会幻觉，太多会失焦。上下文工程 = 主动策划 agent 何时看到什么、以及
如何组织。

## 何时用

- 开始新的编码会话
- agent 输出质量下降（错误模式、幻觉 API、无视项目约定）
- 在代码库不同区域间切换
- 为 AI 辅助开发搭建新项目
- agent 不遵守项目约定

## 上下文层级（从最持久到最易变）

1. **规则文件**（AGENTS.md / CLAUDE.md 等）— 总是加载，全项目生效
2. **规格 / 架构文档** — 按功能/会话加载
3. **相关源文件** — 按任务加载
4. **错误输出 / 测试结果** — 按迭代加载
5. **对话历史** — 累积，可压缩

## 第一层：规则文件（最高杠杆）

维护一个跨会话持续的规则文件（DSH 中是 `AGENTS.md`）：

```markdown
# 项目：<名称>

## 技术栈
- ...

## 命令
- 构建: `...`
- 测试: `...`
- 检查: `...`

## 代码约定
- ...

## 边界（红线）
- 永不提交 .env 或密钥
- 加依赖前先确认
- 改数据库 schema 前先问
- 提交前必跑测试
```

**写规则文件的纪律**：
- 只写**稳定**事实（技术栈、命令、约定、红线），不写易变细节。
- 内容要**可验证**：每条规则都能被检查（"run tests before commit" 可查，
  "write clean code" 不可查）。
- 发现规则过期就更新，不积累"僵尸规则"。

## 第二层：规格/架构文档

- 每个功能/任务有简短 spec（目标、边界、验收标准），用完即弃或归档。
- 架构决策（ADR）单独记录，不进规则文件。

## 第三层：相关源文件

- 按任务只加载相关文件，不整库读。
- 切换区域时主动重新加载目标区域的关键文件，别依赖旧记忆。

## 第四层：错误与测试输出

- 报错时把**完整原文**给 agent（截断会丢信息）。
- 测试结果按迭代反馈，改一处跑一次。

## 第五层：对话历史

- 长会话定期总结关键结论（已定决策、当前任务状态、下一步）。
- 压缩时保留决策和红线，丢弃过程性闲聊。

## 排查流程（输出质量下降时）

1. 检查规则文件是否齐全、过期、有不可验证条目。
2. 检查是否加载了过时/无关的上下文。
3. 检查关键事实是否仍从源码确认（而非依赖记忆）。
4. 逐层修复：先规则文件，再文档，再加载策略。

## 边界

- 上下文工程是"策划信息"，不是"塞入信息"：每加一条上下文都要问
  "这条信息现在真的需要吗？"
- 不为一次性任务写永久规则。
