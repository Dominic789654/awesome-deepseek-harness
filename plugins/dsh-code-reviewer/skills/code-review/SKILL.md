# Code Review — 五轴代码评审

每个变更合并前都要评审——没有例外。评审覆盖五个维度：正确性、可读性、
架构、安全、性能。

**批准标准**：当变更明确提升了整体代码健康时就批准，即使它不完美。
完美代码不存在，目标是持续改进。不要因为"不是我会写的写法"而卡住变更；
只要它改善了代码库并遵循项目约定，就批准。

## 何时用

- 合并任何 PR/变更前
- 完成功能实现后
- 评估其他 agent/模型写的代码
- 重构现有代码时
- 修复 bug 后（同时审修复本身和回归测试）

## 五轴评审

### 1. 正确性
代码做到它声称的事了吗？
- 符合规格/任务要求吗？
- 边界情况处理了吗（null、空、边界值）？
- 错误路径处理了吗（不只快乐路径）？
- 测试都过了吗？测试真的在测对的东西吗？
- 有 off-by-one、竞态、状态不一致吗？

### 2. 可读性与简洁
没有作者解释，另一个工程师/agent 能看懂吗？
- 命名有描述性且符合项目约定吗？（拒绝无上下文的 temp/data/result）
- 控制流直白吗？（避免嵌套三元、深回调）
- 代码组织合理吗？（相关代码分组、模块边界清晰）
- 有没有该简化的"聪明"技巧？
- **能用更少行数吗？**（1000 行能 100 行搞定就是失败）
- **抽象配得上它的复杂度吗？**（不要提前泛化）

### 3. 架构
代码在正确的位置、用正确的方式吗？
- 职责清晰吗？模块边界合理吗？
- 依赖方向正确吗？（高层依赖低层，不反向）
- 有没有重复的"该抽取"的逻辑？
- 与既有架构模式一致吗？
- 可测试性如何？

### 4. 安全
这个变更引入攻击面了吗？
- 输入校验了吗？（不可信数据边界）
- SQL 参数化了吗？输出编码了吗？
- 涉及鉴权/授权变更吗？
- 敏感数据怎么处理？（参考 security-hardening 技能）

### 5. 性能
- 复杂度合理吗？（意外的 O(n²)？N+1 查询？）
- 有该缓存/该懒加载的吗？
- 资源正确释放吗？（连接、文件句柄、定时器）

## 输出格式

```
## 代码评审：<变更>

**结论**：批准 / 需修改 / 拒绝

### 五轴评分
- 正确性：…
- 可读性：…
- 架构：…
- 安全：…
- 性能：…

### 必须修改（blocking）
- …

### 建议改进（非 blocking）
- …

### 值得肯定
- …
```

**分级**：blocking = 正确性/安全问题、明显架构错误；非 blocking = 风格
偏好、可选的简化。批准 = 无 blocking 且整体提升代码健康。

## 纪律

- 先给结论，再给证据（引用具体行/片段）。
- 对事不对人：评审的是代码，不是作者。
- 发现"顺手改"的冲动时克制——只评审，不擅自改（除非被要求）。
