# Git Workflow — git 工作流与版本管理

Git 是你的安全网：提交是存档点，分支是沙盒，历史是文档。AI agent 高速
生成代码时，纪律化的版本控制让变更可管理、可评审、可回退。

## 何时用

始终。每个代码变更都流经 git。

## 核心原则

### 主干开发（推荐）

- `main` 始终可部署。
- 短生命周期特性分支：1-3 天内合回主干。
- 长命分支是隐性成本：分叉、制造冲突、延迟集成。
- DORA 研究持续表明主干开发与高性能工程团队相关。

```
main ──●──●──●──●──●──●──  (始终可部署)
        ╲    ╱
         ●─●─╱   ← 1-3 天特性分支
```

### 提交纪律

- **小而聚焦**：一个提交一件事；提交信息说明"为什么"（不只是"什么"）。
- **频繁提交**：改一点存一点，像游戏存档。
- **提交前自查**：无调试残留、无无关改动、测试通过。
- **信息规范**：建议 Conventional Commits（见 changelog 技能）：
  `feat(scope): 描述` / `fix: ...` / `refactor: ...`。

### 分支策略速查

| 场景 | 做法 |
|---|---|
| 新功能 | `feature/xxx` 短分支 → 合回 main |
| 修复 | 从 main 拉 `fix/xxx` → 修复 → 合回 + 必要时 cherry-pick |
| 发布 | 从 main 打 tag（见下） |
| 并行流 | 短分支隔离；频繁合并减少冲突 |

## 语义化版本

- **MAJOR**：破坏性变更。
- **MINOR**：向后兼容新功能。
- **PATCH**：向后兼容 bug 修复。
- 发布前定版本 → 打 tag（`v1.2.3`）→ 写 changelog（见 changelog 技能）。

## 冲突处理

- 冲突是正常的，说明两边都动了同一处。
- 解决前理解双方意图（读 commit/PR），不盲目保留一方。
- 解决后跑测试；复杂的合并请参考 merge-conflicts 技能。

## 发布流程

1. main 绿（CI 全过）。
2. 定版本号（按语义化版本）。
3. 更新 changelog（Unreleased → 版本号 + 日期）。
4. 打 tag + push tag。
5. 部署/发布 → 验证生产。

## 边界

- 团队已有 git 约定（如 Git Flow、monorepo 工具）时遵循约定。
- 破坏性操作（rebase 已推送分支、force push）先与团队确认。
