# Track-Driven Dev — Track 驱动开发

用 track（逻辑工作单元）组织特性/缺陷/重构：规格 → 计划 → TDD 实施 → 验收。

## 何时用

- 创建/管理特性、缺陷、重构 track
- 写或评审 spec.md
- 创建/更新 plan.md
- 管理 track 从创建到完成的整个生命周期
- 按阶段检查点推进实现
- 管理多 track 并行工作

## 1. Track 管理纪律

- **一个 track 一个关注点**：只做单一逻辑变更
- **小阶段**：每阶段 3-5 个任务封顶
- **阶段后必验证**：每个阶段都含验证任务
- **立即更新标记**：任务状态边做边更
- **记录 SHA**：完成任务记下 commit SHA（可追溯）
- **先规格后计划**：spec 完整才建 plan
- **显式依赖**：track 间依赖写清楚
- **归档不删除**：完成 track 保留供参考
- **规模适当**：1-5 天工作量一个 track
- **验收标准可测**：每个需求可测试

## 2. 实施工作流（TDD + 检查点）

1. **永不跳过 RED**：先写失败测试
2. 小提交：一个逻辑变更一个 commit
3. 任务完成后**立即更新 plan.md**
4. **等审批**：不跳过阶段检查点验证
5. 丰富 git notes：写清上下文帮助未来理解
6. 覆盖率纪律：不低于目标线不验收
7. **质量门全过**才标完成
8. 阶段**顺序推进**；偏离原计划要记录
9. 每个 commit 留下**可运行状态**
10. 开发中频繁跑相关测试（快反馈）
11. 阻塞**及时上报**，不绕行

## 3. 自查清单

- [ ] track 单一关注点、规模 1-5 天、依赖显式
- [ ] spec 完整后 plan 就绪、验收标准可测
- [ ] 先 RED 再实现，每阶段含验证任务
- [ ] plan.md 即时更新、任务状态边做边更
- [ ] 完成任务的 commit SHA 已记录
- [ ] 质量门（覆盖率/测试/检查点）全过才完成
- [ ] 归档完成 track、偏离计划有记录

## 边界

- 适合长周期/多 agent 协作项目；小任务直接做，别过度建 track。
- 具体工具形态（conductor 等）按项目选，纪律本身通用。
