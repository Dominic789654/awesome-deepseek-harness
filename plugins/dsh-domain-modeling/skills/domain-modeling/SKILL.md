# Domain Modeling — 领域建模

在设计过程中**主动**构建并打磨项目的领域模型。这是主动的纪律：挑战术语、
发明边界场景、在概念结晶的当下就把术语表和决策写下来。

（只是"读 CONTEXT.md 取词汇"不算本技能——那是任何技能都能做的一行习惯。
本技能用于**改变**模型，不只是消费它。）

## 文件结构

多数仓库只有一个上下文：

```
/
├── CONTEXT.md          ← 术语表（纯词汇定义，无实现细节）
├── docs/adr/           ← 架构决策记录
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录有 `CONTEXT-MAP.md`，说明有多个上下文，它指向每个上下文的位置。

**惰性创建**：只在有东西要写时才建文件。没有 CONTEXT.md 就在第一个术语
敲定时创建；没有 docs/adr/ 就在第一个 ADR 需要时创建。

## 会话中的纪律

### 对照术语表挑战

用户使用了与 CONTEXT.md 中现有语言冲突的术语时，立即指出：
"你的术语表把 '取消' 定义为 X，但你似乎指的是 Y。到底是哪个？"

### 打磨模糊语言

用户使用含糊/过载的术语时，提出精确的规范术语：
"你说 '账户'：你指的是 Customer 还是 User？这是两个不同的东西。"

### 用具体场景推敲

讨论领域关系时，用具体场景压测：发明探测边界情况的场景，迫使用户
精确界定概念之间的边界。

### 与代码交叉验证

用户陈述"某物如何工作"时，检查代码是否同意。发现矛盾就指出：
"你的代码取消的是整个 Order，但你刚才说部分取消是可能的。哪个对？"

### 即时更新 CONTEXT.md

术语敲定就立刻更新 CONTEXT.md，不要批量攒着。格式：

```markdown
## <术语>

- **定义**：<一句话精确定义>
- **边界**：<它不是什么 / 与相近概念的区分>
- **示例**：<一个具体例子>
```

**CONTEXT.md 必须完全不含实现细节**：它不是 spec、不是草稿、不是
实现决策仓库——它只是术语表。

### 克制地提供 ADR

三个条件**同时**成立才提议建 ADR：

1. **难逆转**：以后改主意的成本很高
2. **无上下文会惊讶**：未来读者会问"为什么这么做？"
3. **真实权衡的结果**：存在真正的替代方案，你因具体理由选了其一

缺任何一个就跳过 ADR。格式：

```markdown
# ADR-000N: <标题>

- **状态**：已接受 / 提议 / 已废弃
- **背景**：问题与约束
- **决策**：选择了什么
- **被否方案**：为什么没选其它
- **后果**：正面与负面
```

## 边界

- 术语表是团队的共享语言，改动要能追溯到对话中的真实分歧或澄清。
- 不为一次性讨论建 ADR；ADR 是留给"未来读者"的。
