# Postmortem — 事故复盘写作

写有效的**无指责**事故复盘：根因分析、时间线、行动项，让组织从每次事故
中学习、防止复发。

## 何时用

- 事故后评审
- 写复盘文档
- 主持无指责复盘会
- 识别根因与促成因素
- 创建可执行跟进项
- 建立组织学习文化

## 核心概念

### 1. 无指责文化

| 指责导向 | 无指责 |
|---|---|
| "谁造成的？" | "什么条件允许了它？" |
| "有人犯了错" | "系统允许了这个错误" |
| 惩罚个人 | 改进系统 |
| 隐藏信息 | 分享经验 |
| 害怕发言 | 心理安全 |

**原则**：人都会犯错；复盘的目的不是找人背锅，而是找出"系统/流程/工具
哪里让错误成为可能"。

### 2. 触发条件

- SEV1/SEV2 事故
- 面向客户的中断 > 15 分钟
- 数据丢失或安全事件
- 任何团队认为值得学习的事件

### 3. 复盘文档结构

```markdown
# 事故复盘：<标题>

- **日期**：YYYY-MM-DD
- **严重度**：SEV1/SEV2/SEV3
- **影响**：<服务/用户/数据受影响范围与时长>

## 摘要
<3-5 句话：发生了什么、为什么、怎么防止>

## 时间线
| 时间 | 事件 |
|---|---|
| HH:MM | 首次告警 |
| HH:MM | 开始调查 |
| HH:MM | 缓解生效 |
| HH:MM | 恢复 |

## 根因分析（5 Whys）
1. 为什么发生？→ …
2. 为什么？→ …
3. …（追问到系统/流程层面，不停在人身上）

## 促成因素
- 缺乏告警 / 手册过时 / 配置缺少 review / …

## 行动项
| 行动 | 负责人 | 截止 | 类型（修复/检测/流程） |
|---|---|---|---|
| … | … | … | … |

## 经验教训
- 我们做对了什么
- 我们做错了什么
- 下次怎么改进
```

### 4. 写作纪律

- **无指责**：不写"某某犯错了"，写"某某操作时，系统没有提供足够的保护/反馈"。
- **时间线用事实**：只记可验证的事件（告警、部署、变更），不记猜测。
- **根因追问到系统层**：5 Whys 至少要问到"为什么系统/流程允许了这个错误"。
- **行动项可执行**：每条有负责人 + 截止 + 类型，不写"加强意识"这种空话。
- **分享学习**：复盘结论可分享（脱敏后），不藏着。

## 边界

- 复盘不是追责会；涉及人事问题时引导到"流程改进"。
- 不编造时间线细节——没有记录的事件标注"待确认"。
