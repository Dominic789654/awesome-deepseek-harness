# Security Requirements — 安全需求提取

把威胁分析转化为可行动的安全需求。

## 何时用

- 威胁模型 → 需求
- 写安全用户故事
- 创建安全测试用例
- 建安全验收标准
- 合规需求映射
- 安全架构文档

## 1. 三层转化

```
业务需求 → 安全需求 → 技术控制
"保护客户数据" → "静态加密 PII" → "AES-256 + KMS 密钥轮换"
```

每层具体化一级，直到可实施可验证。

## 2. 需求类型

| 类型 | 关注 | 示例 |
|---|---|---|
| 功能 | 系统必须做什么 | "系统必须认证用户" |
| 非功能 | 系统必须多好 | "认证必须在 <2s 内完成" |
| 约束 | 施加的限制 | "必须使用批准的加密库" |

## 3. 需求属性

- **可追踪性**：链接到威胁/合规
- **可测性**：可验证
- **优先级**：业务重要性
- **风险等级**：不满足的影响

## 4. 最佳实践

**要**：
- **追踪到威胁**：每条需求映射到威胁
- **具体**：模糊需求无法测试
- **含验收标准**：定义"完成"
- **考虑合规**：尽早映射框架
- **定期评审**：需求随威胁演进

**不要**：
- 不写通用需求（"要安全"不是需求）
- 不省略理由（解释为何重要）
- 不忽视优先级（需求不平等）
- 不忘记可测性（不可测则不可验证）
- 不孤立工作（涉及干系人）

## 5. 自查清单

- [ ] 每条需求追踪到威胁
- [ ] 需求具体（非"要安全"）
- [ ] 含验收标准
- [ ] 合规框架已映射
- [ ] 优先级与风险等级标注
- [ ] 可测性确认 + 干系人参与

## 边界

- 与威胁建模互补：建模发现问题，本技能把它变成可执行需求。
- 需求文档是活的：威胁变化要重新评审。
