# Doubt-Driven Development — 怀疑驱动开发

自信的答案不等于正确的答案。长会话会悄悄把假设变成"事实"而不被注意。
怀疑驱动开发 = 在**任何非平凡输出落地前**，召唤一个"新鲜上下文"的审查者，
它的任务是**证伪**，不是批准。

这不是代码评审（对成品下结论），而是一种**进行中的姿态**：在纠正成本
还便宜的时候，交叉审查非平凡决策。

## 何时用（非平凡的定义）

满足以下**任一**条件即"非平凡"：

- 引入或修改分支逻辑
- 跨越模块/服务边界
- 断言了类型系统无法验证的性质（线程安全、幂等、顺序、不变量）
- 正确性依赖未来读者看不到的上下文
- 爆炸半径不可逆（生产部署、数据迁移、公共 API 变更）

**何时不用**：
- 机械操作（重命名、格式化、移动文件）
- 执行明确的用户指令
- 阅读或总结现有代码
- 一行改动且正确性明显
- 纯工具操作（跑测试、列文件）
- 用户明确要求速度优先于验证

每个键都怀疑，你将一事无成。本技能只适用于上面定义的非平凡决策。

## 五步怀疑循环

```
Doubt cycle:
- [ ] Step 1: CLAIM — 写下断言 + 为什么它重要
- [ ] Step 2: EXTRACT — 剥离出产物 + 契约，去掉推理过程
- [ ] Step 3: DOUBT — 用对抗性提示词召唤新鲜上下文审查者
- [ ] Step 4: RECONCILE — 逐条对照产物文本分类审查发现
- [ ] Step 5: STOP — 满足停止条件（只剩琐碎发现 / 3 轮 / 用户叫停）
```

**Step 1 CLAIM**：用一句话写下你要主张的断言（"这个改动是安全的"
"这个逻辑符合规格"），并说明为什么它值得怀疑（违反直觉？不可验证？）。

**Step 2 EXTRACT**：把断言对应的**产物片段**（代码/配置/结论）与**契约**
（输入输出、不变量）单独抽出来，**剥掉你的推理过程**——审查者只看事实，
不看你的论证，才能发现你论证里的漏洞。

**Step 3 DOUBT**：召唤一个新鲜上下文审查者（DSH 中用子代理/新会话），
给它对抗性提示词："以下产物与契约，请专门找错误：逻辑漏洞、边界条件、
隐含假设、契约违背、并发/幂等/顺序问题。不要夸奖。"

**Step 4 RECONCILE**：把审查发现的每一条，**逐字对照产物**分类：
- 真错误 → 修复
- 有效质疑 → 补验证或改设计
- 误报 → 记录为什么是误报（保留证据，不凭空驳回）

**Step 5 STOP**：停止条件——只剩琐碎发现、已跑 3 轮、或用户叫停。
不要无限循环。

## 纪律

- 审查者必须**新鲜上下文**：带着你整个会话的推理去"自我怀疑"是无效的
  （你会复述自己的错误）。没有子代理时，退化为"自我重写"方案并明确标注
  为降级结果。
- 修复后如果产生了新的非平凡决策，重新进入循环。
- 记录每轮：断言、审查发现、处置。这样用户能看到"怀疑"的账目。

## 与其它技能配合

- 本技能管"决策正确性"，与管"流程"（superpowers-essentials）、
  "代码质量"（karpathy-methodology）互补，可叠加使用。
