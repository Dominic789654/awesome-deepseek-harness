# Karpathy Methodology — 编码方法论

四条纪律，减少 LLM 写代码的常见错误。这些准则偏向"谨慎"而非"速度"；
琐碎任务可凭判断力放宽。

## 1. 先想后写（Think Before Coding）

**不要假设。不要隐藏困惑。把权衡摊开。**

实现前：
- 显式陈述你的假设；不确定就问。
- 存在多种解读时，把它们都列出来——不要默默选一个。
- 有更简单的做法就说出来；该反对时就反对。
- 哪里不清楚就停下，说出困惑点，提问。

## 2. 简单优先（Simplicity First）

**能解决问题的**最小**代码。不做投机性扩展。**

- 不做没被要求的功能。
- 不给一次性代码做抽象。
- 不做没被要求的"灵活性/可配置性"。
- 不为不可能发生的场景写错误处理。
- 如果写了 200 行而 50 行能搞定，重写。

自问："资深工程师会觉得这过度复杂吗？"是，就简化。

## 3. 外科手术式改动（Surgical Changes）

**只碰必须碰的。只清理自己制造的混乱。**

改现有代码时：
- 不"顺手改进"相邻代码、注释或格式。
- 不重构没坏的东西。
- 匹配现有风格，哪怕你会写得不一样。
- 发现无关的死代码，提出来——但不要删。

你的改动产生孤儿时：
- 移除**你的改动**弄成未使用的 import/变量/函数。
- 不要动既有死代码，除非被要求。

检验标准：**每一行改动都能直接追溯到用户的需求。**

## 4. 目标驱动验证（Goal-Driven Execution）

**定义成功标准。循环直到验证通过。**

把任务改写成可验证的目标：
- "加校验" → "写无效输入的测试，然后让它们通过"
- "修 bug" → "写一个能复现它的测试，然后让它通过"
- "重构 X" → "确保重构前后测试都通过"

多步任务先给简短计划：

```
1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
```

强成功标准让你能独立循环；弱标准（"把它弄好"）需要反复澄清。

## 何时用

- 用户开始任何编码任务、改 bug、重构时，本技能的四条纪律应贯穿始终。
- 与"先分类再动手"类方法论技能可叠加使用（本技能管代码质量，后者管流程）。
