# Runbook — 事故手册

生产可用的事故响应手册：检测、分类、缓解、恢复、沟通。手册写给"凌晨三点的
大脑"——步骤要具体到不用思考就能执行。

## 何时用

- 创建事故响应流程
- 搭建服务专属手册
- 建立升级路径
- 记录恢复流程
- 响应进行中的事故
- 培养新的 on-call 工程师

## 1. 严重度分级

| 级别 | 影响 | 响应时间 | 示例 |
|---|---|---|---|
| SEV1 | 完全中断、数据丢失 | 15 分钟 | 生产宕机 |
| SEV2 | 主要功能受损 | 1 小时 | 核心 API 部分失败 |
| SEV3 | 局部/轻微影响 | 4 小时 | 单节点告警 |
| SEV4 | 无用户影响 | 工作时间 | 内部工具问题 |

## 2. 事故响应五阶段

1. **检测**：告警来源（指标/日志/用户报告），确认是否真实事故。
2. **分类**：定严重度、影响范围、是否有缓解（降级/回滚/熔断）。
3. **缓解**（优先于修复）：止血优先——回滚、降级、限流、切流量。
   记录缓解时间点。
4. **恢复**：确认服务恢复、数据一致、监控回绿。
5. **沟通**：对内（升级对象、值班）+ 对外（状态页、客户）的沟通模板。

## 3. 手册模板

```markdown
# <服务> 事故手册

## 服务概述
- 架构位置：…
- 关键依赖：…
- 正常指标基线：…

## 常见事故场景
### 场景 1：<如 连接池耗尽>
- **症状**：…
- **检查**：<1-2-3 具体命令/看板>
- **缓解**：<具体步骤>
- **恢复验证**：…

## 升级路径
- L1 值班 → L2 服务 owner → L3 架构/平台
- 触发条件：<SEV1 立即升级；SEV2 30 分钟未缓解>

## 联系方式
- 值班轮值表：…
- 服务 owner：…
- 外部依赖联系人：…
```

## 4. 值班交接（on-call handoff）

换班时交接：

- 进行中的事故/告警状态
- 近期变更（可能引发问题）
- 未解决的问题与下一步
- 相关链接（手册/看板/聊天记录）

**交接文档结构**：当前状态 → 待办 → 已知风险 → 关键链接。

## 写作纪律

- **写给 3AM 大脑**：步骤具体（命令、路径、看板），不写"检查系统是否正常"
  这种含糊指令。
- **缓解优先**：每场景先给"止血"步骤，再给"根因修复"。
- **保持更新**：手册与现状不符时立即修正，过时手册比没有手册更危险。
- **可执行验证**：每条恢复步骤后有"如何确认恢复"。

## 边界

- 事故中时间紧迫：先缓解、再补文档；手册是辅助不是负担。
- 涉及具体系统配置时以实际环境为准。
