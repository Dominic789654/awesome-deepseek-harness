# Incremental — 增量实现

把大改动拆成**小的、可验证的、保持系统可运行**的步骤。大爆炸式改动
（一次改完再验证）是 bug 与返工的温床；增量推进让每一步都可回退、可审查。

## 核心原则

- **小步**：每步是"最小的有意义推进"，不是"能推多快推多快"。
- **每步可验证**：每步结束系统仍可运行、测试通过（或已知的中间态）。
- **保持可运行**：主干始终可部署（参考 git-workflow 的主干开发）。
- **可回退**：每步小到可以安全回退或重做。

## 增量流程

### 1. 拆步

- 把改动分成按依赖排序的小步（参考 planning 技能）。
- 每步有明确完成标准：做什么 + 怎么验证。

### 2. 逐步入实现

```
Step 1: 地基（接口/数据结构）→ 验证：编译/类型通过
Step 2: 最小可用路径 → 验证：核心用例测试通过
Step 3: 补齐分支 → 验证：边界用例
Step 4: 集成与打磨 → 验证：全量测试 + 手工检查
```

- 每步：实现 → 验证 → 提交（小而聚焦的 commit）。
- 卡住时**保持当前状态可运行**：要么完成小步要么回退，不留半成品。

### 3. 验证推进

- 每步验证通过才进下一步（门控推进）。
- 跨步验证：每 2-3 步跑一次完整测试/构建，确认没有"累积漂移"。

## 增量 vs 大爆炸

| 增量 | 大爆炸 |
|---|---|
| 每步可回退 | 出错难定位 |
| 每步可审查 | 一次 review 量太大 |
| 保持可运行 | 长时间不可运行 |
| 风险分散 | 风险集中到最后 |

**何时可以大爆炸**：改动本身很小且自包含、一次性脚本、纯样式微调。

## 边界

- 增量不是"碎步拖延"：每步要有意义，避免过度拆分导致失去整体视图。
- 与 tdd 配合：每步先写该步的测试（测试驱动增量）。
- 与 planning 配合：先拆计划，再按计划增量执行。
