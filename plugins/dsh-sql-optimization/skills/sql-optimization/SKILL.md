# SQL Optimization — SQL 优化模式

把慢查询变成快查询：系统化优化 + 正确索引 + 查询计划分析。

## 何时用

- 调试慢查询
- 设计高性能 schema
- 优化应用响应时间
- 降低数据库负载/成本
- 大数据量可扩展性
- 分析 EXPLAIN 计划
- 实现高效索引
- 解决 N+1 问题

## 1. 先测量（EXPLAIN）

- 对慢查询跑 `EXPLAIN ANALYZE`（真实执行 + 实际时间）。
- 看关键信号：
  - **Seq Scan 大表** → 缺索引。
  - **Index Scan/Only** → 用上了索引。
  - **行数估计 vs 实际** 差很大 → 统计信息过期（`ANALYZE`）。
  - 排序/哈希/嵌套循环 → 看中间结果大小。

## 2. 索引策略

- 为**实际查询模式**建索引（过滤/排序/join 键），不为所有列建。
- 复合索引：列顺序匹配查询（最左前缀原则）。
- 覆盖索引（Include）：查询只需索引列 → Index Only Scan。
- 部分索引：`WHERE` 条件子集（如活跃用户）。
- 代价：写变慢 + 存储增加——**平衡读写**。

## 3. 常见问题与改写

| 问题 | 改写 |
|---|---|
| N+1（循环查） | join/预加载（批量 IN 查询） |
| SELECT * | 只取需要的列 |
| 函数包裹索引列（`WHERE UPPER(name)`） | 改表达式索引或调整写法 |
| 大表子查询 | join 重写 / CTE 物化 |
| 深分页 `OFFSET` | 游标/键集分页（WHERE id > last） |
| 不必要 DISTINCT/子查询 | 简化（`EXISTS` 优于 `IN` 大表） |

## 4. 查询计划分析流程

1. 慢查询 → EXPLAIN ANALYZE → 找最慢节点。
2. 假设（缺索引？写错？统计旧？）→ 验证（加索引/改写后重测）。
3. 一次改一处，对比前后计划与耗时。

## 5. 防回归

- 关键查询建**性能预算**（超时/耗时阈值告警）。
- 数据量增长时定期复查（explain 计划随分布变化）。
- 新索引/查询走评审（读写权衡）。

## 自查清单

- [ ] 已 EXPLAIN ANALYZE 定位最慢节点
- [ ] 索引匹配实际查询模式（非全列建）
- [ ] 无 N+1、无 SELECT *
- [ ] 无函数包裹索引列
- [ ] 深分页已处理
- [ ] 统计信息新鲜（定期 ANALYZE）

## 边界

- 具体数据库（PG/MySQL）的 EXPLAIN 输出与索引语法不同，按库看。
- 优化要在真实数据规模上验证（小库上"快"不代表生产快）。
