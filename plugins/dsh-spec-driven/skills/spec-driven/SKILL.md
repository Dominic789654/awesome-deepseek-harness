# Spec-Driven — 规格驱动开发

写任何代码之前，先写结构化规格。spec 是你和工程师之间**共享的真源**——
它定义"建什么、为什么、怎么知道完成了"。**没有 spec 的代码是猜测。**

## 何时用

- 开始新项目/新功能
- 需求模糊或不完整
- 改动触及多个文件/模块
- 即将做架构决策
- 实现时间 > 30 分钟的任务

**不用**：单行修复、错别字修正、需求明确且自包含的改动。

## 四阶段门控流程

每个阶段完成后验证，**验证通过才能进入下一阶段**。

### 阶段 1：写 spec

```markdown
# Spec：<功能名>

## 背景
- 问题/动机：…
- 相关上下文：…

## 目标
- 做什么（用户可感知的结果）：…

## 非目标（明确不做）
- …

## 范围与边界
- 输入/输出：…
- 与现有系统交互：…
- 明确不做：…

## 验收标准（可测试）
- [ ] 条件 1（可自动验证）
- [ ] 条件 2
- [ ] 边界情况：…

## 依赖与约束
- 依赖：…  约束：…

## 开放问题
- …
```

### 阶段 2：获批（门控）

- 把 spec 给用户/工程师评审，**得到明确批准**再继续。
- 有分歧先改 spec，不带着分歧写代码。

### 阶段 3：实现

- 严格按 spec 实现，**不擅自加 spec 外功能**。
- 实现中发现 spec 错误 → 停下，先改 spec 再继续。

### 阶段 4：验证

- 逐条跑验收标准，全部通过才算完成。
- 补测试（参考 TDD/测试纪律）。

## 能力地图（可选，复杂需求时）

当一个请求捆绑多个**可独立测试的能力**时，先拆能力地图：

```
能力 A（模块 X）→ 独立 spec A
能力 B（模块 Y）→ 独立 spec B
能力 C（模块 Z）→ 独立 spec C
```

每个能力独立 spec、独立验收、独立排期。

## 纪律

- spec 要**可验证**：验收标准可自动测试，不写"看起来不错"。
- 非目标（不做的事）和范围同等重要，防止范围蔓延。
- spec 是活文档：发现错误就改，但改动要回批（用户知道你在改）。

## 边界

- 琐碎任务（< 30 分钟、单文件、需求明确）不需要完整 spec，简短两句话即可。
- 已有 spec/需求文档的项目，遵循既有文档，不重复写。
