# Agent Teams — 多 agent 团队协作

把一个大任务组织成多个 agent 协作的团队：分角色、分任务、并行推进、
协调集成。适合 DSH 的 subagent 机制。

## 何时用

- 任务可拆成多个独立工作流
- 需要并行调试/并行开发
- 大功能需要分模块实施
- 单 agent 串行太慢

## 1. 团队构成

- **主导者（orchestrator）**：拆任务、派发、汇总、集成（通常是主会话）。
- **执行者（workers）**：每个子任务一个 agent，带完整上下文提示词。
- **评审者（reviewer）**：独立视角评审产物（可选，关键任务加）。
- 角色按需组合，不硬凑"团队"。

## 2. 任务协调

- **拆解**：把大任务拆成可独立验证的子任务（参考 planning）。
- **依赖管理**：标清依赖——独立任务并行，依赖任务排队。
- **接口契约先行**：并行实现前先定义接口（数据格式/函数签名），
  实现者各自对着契约做（参考 parallel-dev）。
- **进度同步**：主导者定期汇总各 worker 状态，处理阻塞。

## 3. 并行工作流

- 每个 worker 的提示词**自包含**：目标、输入、契约、输出格式、
  完成标准、边界（不要依赖共享上下文）。
- 结果返回结构化（JSON/固定格式），便于汇总。
- 失败隔离：单个 worker 失败不拖垮整体；重试或替换。

## 4. 沟通协议

- **上行**：worker 报状态/结果/阻塞给主导者（固定格式）。
- **下行**：主导者下发任务用一致模板（任务/上下文/验收）。
- **旁路**：worker 之间不直接对话——通过主导者协调（避免上下文混乱）。
- **冲突**：发现契约/所有权冲突，立即上报，不擅自改别人的范围。

## 5. 集成与验收

- 汇总各 worker 产物 → 主导者集成 → 跑整体测试。
- 集成问题回溯到对应 worker 修复。
- 团队模式结束时，主导者输出总结（哪些并行有效、哪些阻塞、下次怎么改进）。

## 边界

- 并行有协调成本：任务太小/依赖太紧时串行更快。
- worker 上下文独立：依赖共享状态的任务不适合拆给并行 agent。
- 与 parallel-dev 配合（文件所有权/契约），与 planning 配合（任务拆解）。
