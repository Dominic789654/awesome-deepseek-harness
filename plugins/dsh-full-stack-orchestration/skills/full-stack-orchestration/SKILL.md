# Full-Stack Orchestration — 全栈功能编排

端到端交付一个完整功能：后端 + 前端 + 数据库 + 基础设施，
用状态机保证可恢复、可审查。

## 何时用

- 实现完整全栈功能（垂直切片）
- 涉及前后端 + 数据库 + 部署的多层改动
- 需要分阶段审批的大功能

## 1. 行为铁律

1. **按序执行**：不跳步、不重排、不合并步骤
2. **每步产出文件**：写入 `.full-stack-feature/` 目录，下一步**从文件读**，
   不依赖上下文窗口记忆
3. **检查点停下**：到 PHASE CHECKPOINT 必须停下等用户显式批准
4. **失败即停**：任一步失败（错误/测试失败/缺依赖）→ 停下，呈现错误
   问用户怎么继续，不静默跳过
5. **本地能力**：只用自带的或通用能力，不跨插件依赖

## 2. 状态机（state.json）

```json
{
  "feature": "...", "status": "in_progress",
  "current_step": 1, "current_phase": 1,
  "completed_steps": [], "files_created": [],
  "started_at": "...", "updated_at": "..."
}
```

- 会话恢复：读到 in_progress → 显示当前步骤，让用户选
  "恢复" 或 "从头开始（归档旧会话）"
- 完成状态 → 问是否归档再开新会话

## 3. 分步工作流

1. **需求澄清**：功能描述/技术栈/API 风格/复杂度 → 状态初始化
2. **设计**：数据模型/API 契约/前端结构 → 产出设计文档
3. **后端实现** → 测试
4. **前端实现** → 联调
5. **部署与验证**：环境配置/部署/端到端验证
6. **收尾**：检查点确认 → 状态 complete

每步产出物落盘，检查点处等待批准。

## 4. 自查清单

- [ ] 状态机文件存在且每步更新
- [ ] 每步产出文件，下一步从文件读
- [ ] 检查点处停下等批准
- [ ] 失败即停并呈现错误
- [ ] 恢复路径（in_progress 可续跑）
- [ ] 完成可归档重开

## 边界

- 编排是过程不是银弹：小改动直接做，别上全套流程。
- 检查点数量按复杂度调：简单功能 1-2 个，复杂 3-4 个。
